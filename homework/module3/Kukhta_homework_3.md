# Домашня робота №3: HTTP, TLS та Cookies

## Завдання 1. Аналіз HTTP-заголовків та статус-кодів

### 1.1. Команда

```bash
curl -I http://example.com
```

Параметр `-I` наказує `curl` виконати запит методом `HEAD` і показати лише HTTP-заголовки без тіла сторінки.

### 1.2. Результат виконання

```text
HTTP/1.1 200 OK
Date: Fri, 16 Oct 2026 16:12:59 GMT
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
Last-Modified: Tue, 13 Oct 2026 20:08:28 GMT
Allow: GET, HEAD
Accept-Ranges: bytes
Age: 7583
CF-Cache-Status: HIT
Alt-Svc: h3=":443"; ma=86400
```

### 1.3. Аналіз відповіді

| Параметр | Значення |
|---|---|
| Статус-код | `200 OK` |
| Значення статусу | запит успішно оброблено сервером |
| Заголовок `Location` | відсутній |
| Редирект | не відбувається |
| Версія протоколу | `HTTP/1.1` |

Сервер успішно обробив запит і повернув статус `200 OK`. Заголовка `Location` немає, оскільки сервер не перенаправляє клієнта на іншу адресу. Перший рядок відповіді показує, що для незахищеного запиту було використано протокол HTTP/1.1.

Для порівняння команда `curl -I https://example.com` встановила захищене з’єднання та отримала відповідь `HTTP/2 200`, тобто під час HTTPS-запиту сервер підтримує HTTP/2.

## Завдання 2. Робота з методами HTTP

Для тесту використано API DummyJSON замість забороненого у завданні JSONPlaceholder.

### 2.1. Команда POST

```bash
curl -i -X POST https://dummyjson.com/products/add \
  -H "Content-Type: application/json" \
  -d '{"title":"Network test product","price":100}'
```

### 2.2. Результат виконання

```text
HTTP/2 201
content-type: application/json; charset=utf-8
content-length: 53

{"id":195,"title":"Network test product","price":100}
```

### 2.3. Аналіз результату

Статус-код `201 Created` означає, що сервер успішно прийняв запит і створив новий ресурс. У відповіді сервер повернув створений об’єкт із присвоєним ідентифікатором `195`.

### 2.4. Різниця між GET і POST

| Характеристика | GET | POST |
|---|---|---|
| Основне призначення | отримання ресурсу | передавання даних або створення ресурсу |
| Розташування параметрів | зазвичай у URL після `?` | зазвичай у тілі HTTP-запиту |
| Видимість даних | параметри видно в URL, історії та журналах | дані не додаються до URL, але без HTTPS не є захищеними |
| Кешування | зазвичай може кешуватися | зазвичай не кешується без спеціальних заголовків |
| Ідемпотентність | повторення запиту не повинно змінювати стан сервера | повторення може створити декілька ресурсів |
| Типова успішна відповідь | `200 OK` | `201 Created` або `200 OK` |

GET використовують переважно для читання даних. POST передає дані в тілі запиту та може змінювати стан сервера, наприклад створювати новий ресурс. Передавання даних у тілі POST саме по собі не забезпечує конфіденційність — для цього необхідно використовувати HTTPS.

## Завдання 3. Перевірка TLS-сертифіката

Для перевірки обрано `github.com`, тобто інший сайт замість `google.com`.

### 3.1. Команда

```bash
openssl s_client -connect github.com:443 -servername github.com
```

Параметр `-servername github.com` передає ім’я сервера через SNI, щоб сервер повернув правильний сертифікат для домену.

### 3.2. Основний фрагмент результату

```text
Certificate chain
 0 s:CN=github.com
   i:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36

subject=CN=github.com
issuer=C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36

Verification: OK
New, TLSv1.3, Cipher is TLS_AES_128_GCM_SHA256
Protocol: TLSv1.3
Verify return code: 0 (ok)
```

### 3.3. Аналіз TLS-з’єднання

| Параметр | Значення |
|---|---|
| Сервер | `github.com:443` |
| Власник сертифіката | `CN=github.com` |
| Issuer | `Sectigo Public Server Authentication CA DV E36` |
| Організація видавця | `Sectigo Limited`, Велика Британія |
| Узгоджений протокол | `TLSv1.3` |
| Cipher Suite | `TLS_AES_128_GCM_SHA256` |
| Перевірка сертифіката | `Verify return code: 0 (ok)` |

Сертифікат GitHub виданий центром сертифікації Sectigo. Клієнт і сервер узгодили сучасну версію TLS 1.3 та набір шифрів `TLS_AES_128_GCM_SHA256`. Код перевірки `0` означає, що ланцюжок сертифікатів успішно перевірено.

## Завдання 4. Аналіз безпеки Cookies

Для аналізу використано сайт `github.com`.

### 4.1. Команда

```bash
curl -v -o /dev/null https://github.com 2>&1 | grep -i "< set-cookie"
```

### 4.2. Фрагмент результату

Значення сесійної Cookie приховано, оскільки його не слід публікувати у звітах або репозиторіях.

```text
< set-cookie: _gh_sess=<REDACTED>; path=/; HttpOnly; secure; SameSite=Lax
< set-cookie: _octo=GH1.1.<REDACTED>; expires=Sat, 16 Oct 2027 16:13:00 GMT; domain=.github.com; path=/; secure; SameSite=Lax
< set-cookie: logged_in=no; expires=Sat, 16 Oct 2027 16:13:00 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax
```

### 4.3. Cookie ID та атрибути

| Cookie ID | HttpOnly | Secure | SameSite | Призначення |
|---|---|---|---|---|
| `_gh_sess` | так | так | `Lax` | сесійна Cookie GitHub |
| `_octo` | ні | так | `Lax` | ідентифікатор клієнта |
| `logged_in` | так | так | `Lax` | ознака стану авторизації |

### 4.4. Значення атрибутів безпеки

**HttpOnly** забороняє JavaScript у браузері читати Cookie через `document.cookie`. Це зменшує ризик викрадення сесійного ідентифікатора під час XSS-атаки. Атрибут не усуває саму XSS-вразливість і не заважає браузеру автоматично надсилати Cookie серверу.

**Secure** дозволяє браузеру надсилати Cookie лише через захищене HTTPS-з’єднання. Це зменшує ризик перехоплення Cookie під час передавання через незашифрований HTTP. Атрибут Secure не захищає від XSS і самостійно не шифрує значення Cookie — захист передавання забезпечує TLS.

**SameSite=Lax** обмежує надсилання Cookie під час міжсайтових запитів і зменшує ризик CSRF-атак. Водночас Cookie може надсилатися під час переходу користувача на сайт через звичайне посилання верхнього рівня.

## Завдання 5. Архітектурне моделювання

### 5.1. Сценарій А: оновлення графіків цін у браузері

**Обраний протокол: WebSocket поверх TLS (`wss://`).**

Після початкового HTTP-запиту виконується переключення на постійне двонапрямлене WebSocket-з’єднання. Сервер може надсилати нові ціни браузеру одразу після зміни, без постійного опитування через окремі HTTP-запити.

Переваги WebSocket для цього сценарію:

- мала затримка під час доставки оновлень;
- постійне з’єднання та менші накладні витрати порівняно з HTTP polling;
- сервер може самостійно надсилати дані клієнту;
- браузер може надсилати команди у відповідь, наприклад змінювати список акцій для спостереження;
- `wss://` захищає дані за допомогою TLS.

SSE також підходить для односторонньої передачі цін від сервера до браузера, але WebSocket обрано через двонапрямленість і можливість розширити інтерактивність системи.

### 5.2. Сценарій Б: взаємодія внутрішніх мікросервісів

**Обраний протокол: gRPC поверх HTTP/2 із Protocol Buffers.**

Для взаємодії сервісів білінгу та обліку акцій потрібні низька затримка, надійне передавання і чітко визначені контракти. gRPC використовує компактну бінарну серіалізацію Protocol Buffers та підтримує мультиплексування декількох запитів через одне HTTP/2-з’єднання.

Переваги gRPC для цього сценарію:

- менший обсяг повідомлень порівняно з текстовим JSON;
- низька затримка та повторне використання HTTP/2-з’єднання;
- строгі типи й автоматична генерація клієнтського та серверного коду;
- підтримка звичайних запитів і потокового обміну даними;
- вбудована підтримка deadlines, статусів помилок та автентифікації через TLS.

Для фінансових операцій також потрібні ідемпотентні ідентифікатори операцій, журналювання та повторні спроби лише для безпечних запитів. Якщо система повинна гарантовано зберігати події навіть під час недоступності сервісу, gRPC доцільно доповнити брокером повідомлень, наприклад Kafka або RabbitMQ.

### 5.3. Підсумок вибору

| Сценарій | Обраний протокол | Основна причина |
|---|---|---|
| Браузерні графіки цін | WebSocket через `wss://` | постійне з’єднання та миттєві двонапрямлені оновлення |
| Білінг ↔ облік акцій | gRPC через HTTP/2 і TLS | низька затримка, компактні повідомлення та строгий контракт API |
